# Chapter 9 데이터베이스 관리

> **학습 시간**: 약 4시간  
> **학습 대상**: 데이터베이스를 처음 접하는 학습자  
> **실습 DB**: shopdb

---

## 학습 목표

이 장을 마치면 다음을 할 수 있다.

- 데이터베이스 사용자 계정을 생성하고 삭제할 수 있다.
- GRANT·REVOKE로 사용자에게 적절한 권한을 부여하고 회수할 수 있다.
- mysqldump로 데이터베이스를 백업하고 복원할 수 있다.
- 임시 테이블을 만들어 복잡한 쿼리를 단계별로 처리할 수 있다.

---

## 들어가며 — 왜 관리가 필요한가?

데이터베이스는 여러 사람이 함께 사용하는 공유 자원이다.  
관리가 없으면 세 가지 문제가 생긴다.

**보안 문제**: root 계정을 모든 사람이 쓰면 누구나 모든 데이터를 보고 삭제할 수 있다.  
**장애 복구 문제**: 백업이 없으면 실수로 데이터를 지웠을 때 복구할 방법이 없다.  
**성능 문제**: 쿼리가 복잡해질수록 중간 결과를 임시로 저장하는 방법이 필요하다.

이 장에서는 이 세 가지를 해결하는 방법을 배운다.

## Part 1. 사용자와 권한 관리

## 1. 사용자 계정의 구성

MariaDB의 사용자 계정은 **`'사용자명'@'호스트'`** 형식이다.  
같은 이름이라도 접속 위치(호스트)가 다르면 다른 계정이다.

```
'hong'@'localhost'   → 로컬 서버에서만 접속 가능
'hong'@'%'          → 어떤 호스트에서도 접속 가능
'hong'@'192.168.1.%' → 192.168.1.x 대역에서만 접속 가능
```

> **localhost vs %**: 개발 환경에서는 `localhost`를, 외부 애플리케이션 서버에서 접속할 때는 해당 IP 또는 `%`를 사용한다. 보안상 가능하면 접속 범위를 좁히는 것이 좋다.

---

## 2. 사용자 계정 생성 — CREATE USER

```sql
CREATE USER '사용자명'@'호스트' IDENTIFIED BY '비밀번호';
```

**실습**: shopdb 전용 사용자 계정 생성

```sql
-- 로컬 접속 전용 개발자 계정
CREATE USER 'shopdev'@'localhost' IDENTIFIED BY 'Dev@1234!';

-- 외부 애플리케이션 서버 계정 (모든 호스트 허용)
CREATE USER 'shopapp'@'%' IDENTIFIED BY 'App@1234!';

-- 읽기 전용 분석가 계정
CREATE USER 'shopread'@'localhost' IDENTIFIED BY 'Read@1234!';
```

> **비밀번호 규칙**: MariaDB는 기본적으로 복잡한 비밀번호를 권장한다.  
> 영문 대소문자, 숫자, 특수문자를 조합하는 것이 좋다.

## 3. 사용자 목록 조회

```sql
-- 현재 데이터베이스의 사용자 목록
SELECT user, host FROM mysql.user;
```

실행 결과:
```
+----------+-----------+
| user     | host      |
+----------+-----------+
| root     | localhost |
| shopapp  | %         |
| shopdev  | localhost |
| shopread | localhost |
+----------+-----------+
```

> `mysql.user`는 MariaDB가 사용자 정보를 저장하는 시스템 테이블이다.

## 4. 권한 부여 — GRANT

```sql
GRANT 권한목록 ON 데이터베이스.테이블 TO '사용자명'@'호스트';
```

**권한 범위 표기**

| 표기 | 적용 범위 |
|---|---|
| `*.*` | 모든 데이터베이스의 모든 테이블 |
| `shopdb.*` | shopdb의 모든 테이블 |
| `shopdb.product` | shopdb의 product 테이블만 |

**주요 권한**

| 권한 | 설명 |
|---|---|
| `SELECT` | 데이터 조회 |
| `INSERT` | 데이터 삽입 |
| `UPDATE` | 데이터 수정 |
| `DELETE` | 데이터 삭제 |
| `CREATE` | 테이블·DB 생성 |
| `DROP` | 테이블·DB 삭제 |
| `ALTER` | 테이블 구조 변경 |
| `INDEX` | 인덱스 생성·삭제 |
| `ALL PRIVILEGES` | 모든 권한 |

---

### 4.1 역할별 권한 부여 실습

**개발자 계정** — DML 전체 + 구조 변경 권한

```sql
GRANT SELECT, INSERT, UPDATE, DELETE, CREATE, ALTER, INDEX
    ON shopdb.*
    TO 'shopdev'@'localhost';
```

**애플리케이션 서버 계정** — DML만 (DELETE 제외)

```sql
GRANT SELECT, INSERT, UPDATE
    ON shopdb.*
    TO 'shopapp'@'%';
```

> 애플리케이션 서버에 DELETE 권한을 주지 않으면 소프트웨어 버그로 인한 데이터 삭제 사고를 예방할 수 있다.

**읽기 전용 분석가 계정** — SELECT만

```sql
GRANT SELECT
    ON shopdb.*
    TO 'shopread'@'localhost';
```

**특정 테이블만 접근 가능한 계정**

```sql
-- product, category 테이블만 SELECT 가능
GRANT SELECT ON shopdb.product  TO 'shopread'@'localhost';
GRANT SELECT ON shopdb.category TO 'shopread'@'localhost';
```

**권한 부여 후 즉시 적용**

```sql
FLUSH PRIVILEGES;
```

> 일반적으로 `GRANT`를 사용하면 자동 반영되지만, 시스템 테이블을 직접 수정한 경우에는 `FLUSH PRIVILEGES`로 명시적으로 적용해야 한다.

---

## 5. 권한 확인 — SHOW GRANTS

```sql
-- 특정 사용자의 권한 확인
SHOW GRANTS FOR 'shopdev'@'localhost';
```

실행 결과:
```
+----------------------------------------------------------------------------------------------+
| Grants for shopdev@localhost                                                                 |
+----------------------------------------------------------------------------------------------+
| GRANT USAGE ON *.* TO `shopdev`@`localhost` IDENTIFIED BY PASSWORD '...'                    |
| GRANT SELECT, INSERT, UPDATE, DELETE, CREATE, ALTER, INDEX ON `shopdb`.* TO `shopdev`@`localhost` |
+----------------------------------------------------------------------------------------------+
```

- 첫 번째 줄: 계정 존재 자체에 대한 기본 권한 (`USAGE`)
- 두 번째 줄: shopdb에 부여된 실제 권한

```sql
-- 현재 로그인한 자신의 권한 확인
SHOW GRANTS;
SHOW GRANTS FOR CURRENT_USER();
```

---

## 6. 권한 회수 — REVOKE

```sql
REVOKE 권한목록 ON 데이터베이스.테이블 FROM '사용자명'@'호스트';
```

**실습**: 개발자 계정에서 DROP 권한 회수

```sql
-- shopdev에게 실수로 DROP 권한을 줬다면
GRANT DROP ON shopdb.* TO 'shopdev'@'localhost';

-- 회수
REVOKE DROP ON shopdb.* FROM 'shopdev'@'localhost';

-- 확인
SHOW GRANTS FOR 'shopdev'@'localhost';
```

**모든 권한 한 번에 회수**

```sql
REVOKE ALL PRIVILEGES ON shopdb.* FROM 'shopapp'@'%';
```

---

## 7. 비밀번호 변경

```sql
-- 특정 사용자의 비밀번호 변경 (관리자 권한 필요)
ALTER USER 'shopdev'@'localhost' IDENTIFIED BY 'NewDev@5678!';

-- 자신의 비밀번호 변경
ALTER USER CURRENT_USER() IDENTIFIED BY 'NewPassword!';

-- 비밀번호 변경 후 즉시 적용
FLUSH PRIVILEGES;
```

## 8. 사용자 계정 삭제 — DROP USER

```sql
DROP USER '사용자명'@'호스트';
DROP USER IF EXISTS '사용자명'@'호스트';  -- 없어도 오류 없이 실행
```

```sql
-- 더 이상 필요 없는 계정 삭제
DROP USER IF EXISTS 'shopread'@'localhost';
```

> **주의**: 사용자를 삭제하면 해당 사용자에게 부여된 권한도 함께 삭제된다.  
> 단, 그 사용자가 만든 테이블이나 데이터는 삭제되지 않는다.

---

### 8.1 권한 관리 전체 흐름 요약

```
1. 계정 생성    CREATE USER 'shopdev'@'localhost' IDENTIFIED BY '비밀번호';
2. 권한 부여    GRANT SELECT, INSERT, UPDATE, DELETE ON shopdb.* TO 'shopdev'@'localhost';
3. 권한 확인    SHOW GRANTS FOR 'shopdev'@'localhost';
4. 권한 회수    REVOKE DELETE ON shopdb.* FROM 'shopdev'@'localhost';
5. 계정 삭제    DROP USER 'shopdev'@'localhost';
```

## 9. 백업이 중요한 이유

데이터베이스에는 예상치 못한 사고가 언제든 생길 수 있다.

- 실수로 `DELETE FROM orders;` (WHERE 없이) 실행
- 하드웨어 고장으로 데이터 손실
- 악의적인 공격으로 데이터 훼손
- 잘못된 마이그레이션으로 데이터 오염

백업이 없으면 이런 상황에서 데이터를 되돌릴 방법이 없다.  
"백업은 있을 때는 필요 없고, 없을 때 반드시 필요하다"는 말처럼 평소에 준비해야 한다.

---

## 10. mysqldump — 논리 백업

**mysqldump**는 데이터베이스의 내용을 SQL 구문(CREATE TABLE + INSERT)으로 내보내는 도구다.  
`mysqldump`는 SQL 클라이언트가 아닌 **운영체제 명령 프롬프트(터미널)**에서 실행한다.

> MariaDB 10.4 이후에는 `mariadb-dump`라는 이름도 사용할 수 있다. 기능은 동일하다.

---

### 10.1 데이터베이스 전체 백업

```bash
# 명령 프롬프트 / 터미널에서 실행
mysqldump -u root -p shopdb > shopdb_backup.sql
```

| 옵션 | 설명 |
|---|---|
| `-u root` | 접속 사용자 |
| `-p` | 비밀번호 입력 요청 |
| `shopdb` | 백업할 데이터베이스 이름 |
| `> shopdb_backup.sql` | 결과를 파일로 저장 |

실행하면 비밀번호를 입력하라는 프롬프트가 나타난다:
```
Enter password: ********
```

생성된 `shopdb_backup.sql` 파일의 내용 일부:
```sql
-- MariaDB dump 10.19
-- Host: localhost    Database: shopdb
-- ------------------------------------------------------

CREATE DATABASE IF NOT EXISTS `shopdb`;
USE `shopdb`;

DROP TABLE IF EXISTS `category`;
CREATE TABLE `category` (
  `category_id` int(11) NOT NULL AUTO_INCREMENT,
  `category_name` varchar(50) NOT NULL,
  PRIMARY KEY (`category_id`)
) ENGINE=InnoDB;

INSERT INTO `category` VALUES (1,'전자기기'),(2,'주방용품')...
```

---

### 10.2 특정 테이블만 백업

```bash
# product와 category 테이블만 백업
mysqldump -u root -p shopdb product category > shopdb_tables.sql
```

---

### 10.3 여러 데이터베이스 백업

```bash
# 여러 DB를 한 파일에 백업
mysqldump -u root -p --databases shopdb testdb > multi_backup.sql

# 서버의 모든 DB 백업
mysqldump -u root -p --all-databases > all_backup.sql
```

---

### 10.4 자주 쓰는 옵션

| 옵션 | 설명 |
|---|---|
| `--no-data` (`-d`) | 구조(DDL)만 백업, 데이터 제외 |
| `--no-create-info` (`-t`) | 데이터만 백업, 테이블 구조 제외 |
| `--single-transaction` | InnoDB 테이블을 잠금 없이 일관성 있게 백업 |
| `--routines` (`-R`) | 저장 프로시저·함수도 함께 백업 |
| `--triggers` | 트리거도 함께 백업 |
| `--compress` | 네트워크 전송 시 압축 |

```bash
# 구조만 백업 (데이터 없이)
mysqldump -u root -p --no-data shopdb > shopdb_schema.sql

# 일관성 있는 InnoDB 백업 (운영 중 백업에 권장)
mysqldump -u root -p --single-transaction shopdb > shopdb_backup.sql
```

---

### 10.5 날짜를 파일명에 포함하기 (Windows)

```batch
REM Windows 명령 프롬프트
mysqldump -u root -p shopdb > shopdb_%date:~0,4%%date:~5,2%%date:~8,2%.sql
REM 예: shopdb_20240725.sql
```

```bash
# Linux / macOS
mysqldump -u root -p shopdb > shopdb_$(date +%Y%m%d).sql
# 예: shopdb_20240725.sql
```

## 11. 데이터베이스 복원

백업 파일을 `mysql` 명령으로 데이터베이스에 다시 불러온다.

```bash
# 복원 (DB가 이미 존재해야 함)
mysql -u root -p shopdb < shopdb_backup.sql

# DB가 없으면 먼저 생성
mysql -u root -p -e "CREATE DATABASE shopdb;"
mysql -u root -p shopdb < shopdb_backup.sql
```

> **`-e` 옵션**: 명령 프롬프트에서 SQL을 한 줄 실행하는 옵션이다.

---

### 11.1 복원 절차 실습

```bash
# 1단계: 현재 shopdb 백업
mysqldump -u root -p shopdb > shopdb_backup_20240725.sql

# 2단계: 실수 시뮬레이션 (MariaDB 클라이언트에서)
#   mysql> DELETE FROM order_detail;
#   mysql> DELETE FROM orders;

# 3단계: 복원
mysql -u root -p shopdb < shopdb_backup_20240725.sql

# 4단계: 복원 확인 (MariaDB 클라이언트에서)
#   mysql> SELECT COUNT(*) FROM orders;      -- 결과: 10
#   mysql> SELECT COUNT(*) FROM order_detail; -- 결과: 10
```

---

### 11.2 백업 파일을 MariaDB 클라이언트 내에서 실행

MariaDB 클라이언트에 이미 접속해 있다면 `SOURCE` 명령을 사용할 수 있다.

```sql
-- MariaDB 클라이언트 내부에서 실행
SOURCE C:/backup/shopdb_backup_20240725.sql;

-- Linux / macOS 경로 형식
SOURCE /home/user/backup/shopdb_backup_20240725.sql;
```

---

### 11.3 백업 전략

| 전략 | 설명 | 권장 상황 |
|---|---|---|
| 전체 백업 | 모든 데이터를 매번 백업 | 데이터양이 적을 때 |
| 일별 자동 백업 | 매일 특정 시간에 자동 실행 | 운영 환경 기본 |
| 변경 전 백업 | 중요 작업(스키마 변경 등) 전 즉시 백업 | 항상 권장 |

> **실무 원칙**: 중요한 작업(ALTER TABLE, 대량 UPDATE/DELETE) 전에는 반드시 백업 먼저.  
> "나중에 백업하지"는 항상 나중에 후회하게 된다.

## 12. 임시 테이블이란?

**임시 테이블(Temporary Table)**은 현재 세션(접속)에서만 존재하는 테이블이다.  
세션이 종료(접속 끊김)되면 자동으로 사라진다.

### 임시 테이블이 필요한 경우

복잡한 쿼리를 한 번에 작성하기 어려울 때 중간 결과를 저장하고 단계별로 처리할 수 있다.

```
[단계 1] 고객별 총 구매금액 계산  →  임시 테이블 저장
[단계 2] 임시 테이블에서 50만 원 이상 고객 필터
[단계 3] 원본 customer 테이블과 조인하여 최종 결과 출력
```

## 13. 임시 테이블 생성

### 13.1 CREATE TEMPORARY TABLE — 직접 정의

```sql
CREATE TEMPORARY TABLE 임시테이블명 (
    컬럼명 데이터타입,
    ...
);
```

```sql
-- 재고 부족 상품을 담을 임시 테이블 직접 생성
CREATE TEMPORARY TABLE temp_low_stock (
    product_id   INT,
    product_name VARCHAR(100),
    stock        INT,
    price        INT
);

-- 데이터 삽입
INSERT INTO temp_low_stock
SELECT product_id, product_name, stock, price
FROM product
WHERE stock < 20;

-- 조회
SELECT * FROM temp_low_stock ORDER BY stock;
```

실행 결과:
```
+------------+------------------------+-------+--------+
| product_id | product_name           | stock | price  |
+------------+------------------------+-------+--------+
|          9 | 원목 1인 책상           |    10 | 185000 |
|          4 | 스테인리스 전기주전자    |    15 |  42000 |
+------------+------------------------+-------+--------+
```

---

### 13.2 CREATE TEMPORARY TABLE ... AS SELECT — 조회 결과로 즉시 생성

```sql
CREATE TEMPORARY TABLE 임시테이블명 AS
SELECT ...;
```

구조 정의 없이 SELECT 결과의 구조와 데이터를 한 번에 임시 테이블로 만든다.

**예제 1**: 고객별 총 구매금액 임시 테이블

```sql
CREATE TEMPORARY TABLE temp_customer_total AS
SELECT
    o.customer_id,
    SUM(d.quantity * d.unit_price) AS total_spent
FROM orders o
JOIN order_detail d ON o.order_id = d.order_id
GROUP BY o.customer_id;

-- 확인
SELECT * FROM temp_customer_total ORDER BY total_spent DESC;
```

실행 결과:
```
+-------------+-------------+
| customer_id | total_spent |
+-------------+-------------+
|           6 |     185,000 |
|           1 |     156,000 |
|           2 |     103,000 |
|           4 |      54,000 |
|           5 |      42,000 |
|           3 |      32,000 |
|           8 |           0 |
|           7 |           0 |
+-------------+-------------+
```

> `customer_id 7, 8`(강지우, 조현우)은 주문이 있지만 order_detail 행이 없어 합계 0원.  
> `customer_id 9, 10`(임서연, 윤도현)은 주문 자체가 없어 결과에 나타나지 않는다.

---

**예제 2**: 임시 테이블을 이용한 단계별 처리

```sql
-- 1단계: 총 구매금액 50,000원 이상인 고객 ID만 저장
CREATE TEMPORARY TABLE temp_high_value AS
SELECT customer_id, total_spent
FROM temp_customer_total
WHERE total_spent >= 50000;

-- 2단계: customer 테이블과 조인하여 고객 정보 출력
SELECT
    c.name          AS 고객명,
    c.email,
    t.total_spent   AS 총구매금액
FROM customer c
JOIN temp_high_value t ON c.customer_id = t.customer_id
ORDER BY t.total_spent DESC;
```

실행 결과:
```
+--------+------------------+-------------+
| 고객명  | email            | 총구매금액   |
+--------+------------------+-------------+
| 정태양  | jung@example.com |     185,000 |
| 홍길동  | hong@example.com |     156,000 |
| 김영희  | kim@example.com  |     103,000 |
| 박민준  | park@example.com |      54,000 |
+--------+------------------+-------------+
```

**예제 3**: 복잡한 보고서를 임시 테이블로 단순화

```sql
-- 1단계: 주문별 총액 임시 저장
CREATE TEMPORARY TABLE temp_order_amount AS
SELECT
    order_id,
    SUM(quantity * unit_price) AS order_total
FROM order_detail
GROUP BY order_id;

-- 2단계: 평균보다 높은 주문 조회
SELECT
    o.order_id,
    c.name      AS 고객명,
    t.order_total,
    o.status
FROM orders o
JOIN customer c        ON o.customer_id = c.customer_id
JOIN temp_order_amount t ON o.order_id   = t.order_id
WHERE t.order_total > (SELECT AVG(order_total) FROM temp_order_amount)
ORDER BY t.order_total DESC;
```

실행 결과 (평균 ≒ 72,142원):
```
+----------+--------+-------------+-----------+
| order_id | 고객명  | order_total | status    |
+----------+--------+-------------+-----------+
|        7 | 정태양  |     185,000 | 배송중     |
|        1 | 홍길동  |      85,000 | 배송완료   |
|        3 | 홍길동  |      71,000 | 배송완료   |  ← 평균에 근접, 포함 여부는 실제 AVG 확인
+----------+--------+-------------+-----------+
```

## 14. 임시 테이블 vs 일반 테이블

| 항목 | 임시 테이블 | 일반 테이블 |
|---|:---:|:---:|
| 세션 종료 시 자동 삭제 | ✅ | ❌ |
| 다른 세션에서 접근 | ❌ 불가 | ✅ 가능 |
| 일반 테이블과 이름 충돌 | 임시 테이블 우선 | - |
| 인덱스 생성 가능 | ✅ | ✅ |
| 트랜잭션 지원 | ✅ (InnoDB) | ✅ |

> **이름 충돌 주의**: 임시 테이블과 일반 테이블 이름이 같으면 임시 테이블이 우선된다.  
> 세션 내에서 일반 테이블에 접근하려면 임시 테이블을 먼저 삭제해야 한다.

---

## 15. 임시 테이블 삭제 — DROP TEMPORARY TABLE

세션 종료 시 자동으로 사라지지만, 명시적으로 삭제하면 메모리를 즉시 반환할 수 있다.

```sql
DROP TEMPORARY TABLE 임시테이블명;
DROP TEMPORARY TABLE IF EXISTS 임시테이블명;
```

```sql
-- 실습 후 정리
DROP TEMPORARY TABLE IF EXISTS temp_customer_total;
DROP TEMPORARY TABLE IF EXISTS temp_high_value;
DROP TEMPORARY TABLE IF EXISTS temp_order_amount;
DROP TEMPORARY TABLE IF EXISTS temp_low_stock;
```

> `DROP TABLE`(TEMPORARY 없이)도 임시 테이블을 삭제하지만, 같은 이름의 일반 테이블이 있으면 잘못 삭제할 수 있다. `DROP TEMPORARY TABLE`을 쓰는 것이 안전하다.

---

### ✅ 확인 문제 3

1. `product` 테이블에서 가격(`price`)이 30,000원 이상인 상품을 `temp_expensive`라는 임시 테이블로 만드는 SQL을 작성하시오.
2. 앞에서 만든 `temp_expensive`를 `category` 테이블과 조인하여 카테고리별 고가 상품 수를 조회하시오.
3. 임시 테이블과 일반 테이블의 차이점 세 가지를 설명하시오.
4. 임시 테이블이 유용한 시나리오를 하나 들어 설명하시오.

> **정답**:
> ```sql
> -- 1
> CREATE TEMPORARY TABLE temp_expensive AS
> SELECT product_id, product_name, price, category_id
> FROM product
> WHERE price >= 30000;
> -- 결과: USB 허브(35,000), 블루투스 키보드(55,000), 전기주전자(42,000),
> --       요가매트(32,000), 원목 책상(185,000) → 5개 상품
>
> -- 2
> SELECT c.category_name, COUNT(*) AS 고가상품수
> FROM temp_expensive t
> JOIN category c ON t.category_id = c.category_id
> GROUP BY c.category_name
> ORDER BY 고가상품수 DESC;
>
> -- 3
> ① 임시 테이블은 세션이 종료되면 자동으로 삭제되고, 일반 테이블은 명시적으로 DROP해야 삭제된다.
> ② 임시 테이블은 생성한 세션에서만 보이며, 다른 세션에서는 접근할 수 없다.
> ③ 같은 이름의 일반 테이블이 있을 때 임시 테이블이 우선 접근된다.
>
> -- 4
> 예) 여러 테이블을 조인한 복잡한 집계 결과를 임시 테이블에 저장한 뒤,
>     그 결과를 다시 필터링하거나 추가 조인에 활용하면 쿼리를 단계별로 나눌 수 있어
>     가독성과 유지보수성이 높아진다.
>     인라인 뷰(서브쿼리)로 처리하면 쿼리가 너무 복잡해질 때 유용하다.
> ```

### 사용자·권한 관리

| 구문 | 설명 |
|---|---|
| `CREATE USER '계정'@'호스트' IDENTIFIED BY '비밀번호'` | 계정 생성 |
| `SELECT user, host FROM mysql.user` | 계정 목록 조회 |
| `GRANT 권한 ON DB.테이블 TO '계정'@'호스트'` | 권한 부여 |
| `SHOW GRANTS FOR '계정'@'호스트'` | 권한 확인 |
| `REVOKE 권한 ON DB.테이블 FROM '계정'@'호스트'` | 권한 회수 |
| `ALTER USER '계정'@'호스트' IDENTIFIED BY '비밀번호'` | 비밀번호 변경 |
| `DROP USER '계정'@'호스트'` | 계정 삭제 |
| `FLUSH PRIVILEGES` | 권한 즉시 적용 |

### 백업·복원

| 구문 | 설명 |
|---|---|
| `mysqldump -u root -p DB > 파일.sql` | 전체 백업 |
| `mysqldump -u root -p DB 테이블1 테이블2 > 파일.sql` | 테이블 선택 백업 |
| `mysqldump -u root -p --no-data DB > 파일.sql` | 구조만 백업 |
| `mysql -u root -p DB < 파일.sql` | 복원 |
| `SOURCE 파일경로;` | 클라이언트 내부에서 복원 |

### 임시 테이블

| 구문 | 설명 |
|---|---|
| `CREATE TEMPORARY TABLE 이름 (컬럼 ...)` | 임시 테이블 직접 생성 |
| `CREATE TEMPORARY TABLE 이름 AS SELECT ...` | 조회 결과로 임시 테이블 생성 |
| `DROP TEMPORARY TABLE IF EXISTS 이름` | 임시 테이블 삭제 |

임시 테이블은 세션 종료 시 자동으로 삭제되며 다른 세션에서는 접근할 수 없다.
