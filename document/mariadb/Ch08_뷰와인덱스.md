## 1. 뷰란?

**뷰(View)**는 SELECT 쿼리를 저장해 두고 마치 테이블처럼 사용할 수 있는 **가상 테이블**이다.  
뷰 자체에 데이터가 저장되는 것이 아니라, 뷰를 조회할 때마다 원본 SELECT가 실행된다.

### 뷰가 필요한 이유

실무에서는 여러 테이블을 조인하거나 복잡한 조건을 걸어야 원하는 데이터를 얻을 수 있다.  
이런 쿼리를 매번 반복하면 실수하기 쉽고, 코드가 길어진다.  
뷰를 사용하면 복잡한 쿼리를 한 번 정의해 두고 간단하게 재사용할 수 있다.

```
원본 테이블들                  뷰
┌──────────┐              ┌──────────────────┐
│ orders   │──┐           │ v_order_summary  │
├──────────┤  ├─(JOIN)──▶ │                  │
│ customer │──┤           │ 가상 테이블로     │
├──────────┤  │           │ 단순 SELECT 가능 │
│ order_   │──┘           └──────────────────┘
│ detail   │
└──────────┘
```

**뷰의 장점**

| 장점 | 설명 |
|---|---|
| **재사용성** | 복잡한 JOIN·집계 쿼리를 한 번 정의하면 반복 사용 가능 |
| **보안** | 민감한 컬럼(비밀번호, 개인정보 등)을 숨기고 필요한 컬럼만 노출 |
| **단순화** | 사용자는 복잡한 쿼리 구조를 몰라도 뷰만 SELECT |
| **유지보수** | 쿼리 변경이 필요할 때 뷰 정의만 수정하면 모든 곳에 반영 |

## 2. 뷰 생성 — CREATE VIEW

```sql
CREATE VIEW 뷰이름 AS
SELECT ...;
```

뷰 이름은 보통 `v_` 접두사를 붙여 테이블과 구분한다.

---

### 2.1 단순 뷰 — 단일 테이블, 컬럼 제한

**예제**: 상품 테이블에서 전자기기(category_id=1)만 보는 뷰

```sql
CREATE VIEW v_electronics AS
SELECT
    product_id,
    product_name,
    price,
    stock
FROM product
WHERE category_id = 1;
```

생성 후 일반 테이블처럼 조회:

```sql
SELECT * FROM v_electronics;
```

실행 결과:
```
+------------+------------------+-------+-------+
| product_id | product_name     | price | stock |
+------------+------------------+-------+-------+
|          1 | 무선 마우스       | 25000 |    50 |
|          2 | USB 4포트 허브   | 35000 |    30 |
|          3 | 블루투스 키보드   | 55000 |    20 |
+------------+------------------+-------+-------+
```

### 2.2 조인 뷰 — 여러 테이블 결합

**예제**: 상품과 카테고리 이름을 함께 보는 뷰

```sql
CREATE VIEW v_product_category AS
SELECT
    p.product_id,
    p.product_name,
    c.category_name,
    p.price,
    p.stock
FROM product p
JOIN category c ON p.category_id = c.category_id;
```

조회:

```sql
SELECT * FROM v_product_category ORDER BY product_id;
```

실행 결과:
```
+------------+------------------------+---------------+--------+-------+
| product_id | product_name           | category_name | price  | stock |
+------------+------------------------+---------------+--------+-------+
|          1 | 무선 마우스             | 전자기기       | 25000  |    50 |
|          2 | USB 4포트 허브         | 전자기기       | 35000  |    30 |
|          3 | 블루투스 키보드         | 전자기기       | 55000  |    20 |
|          4 | 스테인리스 전기주전자    | 주방용품       | 42000  |    15 |
|          5 | MariaDB 입문           | 도서           | 28000  | 100  |
|          6 | 요가매트 6mm           | 스포츠용품     | 32000  |    40 |
|          7 | 코튼 반팔 티셔츠        | 의류           | 18000  |   200 |
|          8 | 비타민C 1000mg         | 뷰티/헬스      | 15000  |   150 |

뷰를 만든 뒤에는 WHERE, ORDER BY, LIMIT도 그대로 사용할 수 있다.

```sql
-- 카테고리별 상품 수 집계
SELECT category_name, COUNT(*) AS 상품수
FROM v_product_category
GROUP BY category_name
ORDER BY 상품수 DESC;
```

### 2.3 집계 뷰 — GROUP BY 포함

**예제**: 주문 요약 뷰 (고객명, 주문일, 총금액 포함)

```sql
CREATE VIEW v_order_summary AS
SELECT
    o.order_id,
    c.name                          AS customer_name,
    o.order_date,
    SUM(d.quantity * d.unit_price)  AS total_amount,
    o.status
FROM orders o
JOIN customer     c ON o.customer_id = c.customer_id
LEFT JOIN order_detail d ON o.order_id = d.order_id
GROUP BY o.order_id, c.name, o.order_date, o.status;
```

> LEFT JOIN을 사용한 이유: order_id 9, 10은 order_detail 행이 없다.  
> INNER JOIN을 쓰면 이 두 주문이 결과에서 빠진다.

조회:

```sql
SELECT * FROM v_order_summary ORDER BY order_id;
```

실행 결과:
```
+----------+---------------+---------------------+--------------+-----------+
| order_id | customer_name | order_date          | total_amount | status    |
+----------+---------------+---------------------+--------------+-----------+
|        1 | 홍길동         | 2024-01-15 10:23:00 |       85,000 | 배송완료   |
|        2 | 김영희         | 2024-02-03 14:05:00 |       55,000 | 배송완료   |
|        3 | 홍길동         | 2024-02-20 09:47:00 |       71,000 | 배송완료   |
|        4 | 이철수         | 2024-03-05 16:30:00 |       32,000 | 배송완료   |

### 2.4 고객 통계 뷰

**예제**: 고객별 주문 건수와 총 구매 금액

```sql
CREATE VIEW v_customer_stats AS
SELECT
    c.customer_id,
    c.name,
    COUNT(DISTINCT o.order_id)       AS order_count,
    COALESCE(SUM(d.quantity * d.unit_price), 0) AS total_spent
FROM customer c
LEFT JOIN orders o       ON c.customer_id = o.customer_id
LEFT JOIN order_detail d ON o.order_id    = d.order_id
GROUP BY c.customer_id, c.name;
```

조회:

```sql
SELECT * FROM v_customer_stats ORDER BY total_spent DESC;
```

실행 결과:
```
+-------------+--------+-------------+-------------+
| customer_id | name   | order_count | total_spent |
+-------------+--------+-------------+-------------+
|           6 | 정태양  |           1 |     185,000 |
|           1 | 홍길동  |           2 |     156,000 |
|           2 | 김영희  |           2 |     103,000 |
|           4 | 박민준  |           1 |      54,000 |
|           3 | 이철수  |           1 |      32,000 |
|           5 | 최수연  |           1 |      42,000 |
|           7 | 강지우  |           1 |           0 |
|           8 | 조현우  |           1 |           0 |
|           9 | 임서연  |           0 |           0 |
|          10 | 윤도현  |           0 |           0 |
+-------------+--------+-------------+-------------+
```

> `COALESCE(SUM(...), 0)`: 주문이 없거나 주문 상세가 없으면 SUM이 NULL을 반환한다. COALESCE로 0으로 대체했다.

## 3. 뷰 수정 — CREATE OR REPLACE VIEW

뷰를 수정하려면 `CREATE OR REPLACE VIEW`를 사용한다.  
기존 뷰가 없으면 새로 만들고, 있으면 교체한다.

```sql
-- price가 3만 원 미만인 전자기기만 보도록 뷰 조건 수정
CREATE OR REPLACE VIEW v_electronics AS
SELECT
    product_id,
    product_name,
    price,
    stock
FROM product
WHERE category_id = 1
  AND price < 30000;
```

## 6. 업데이트 가능한 뷰

단순한 뷰는 SELECT뿐 아니라 INSERT, UPDATE, DELETE도 실행할 수 있다.  
단, 다음 조건을 **하나라도 포함하면** 업데이트가 불가능하다.

| 포함 여부 | 업데이트 가능 여부 |
|---|:---:|
| 단일 테이블 SELECT | ✅ 가능 |
| 집계 함수 (COUNT, SUM, AVG ...) | ❌ 불가 |
| GROUP BY / HAVING | ❌ 불가 |
| DISTINCT | ❌ 불가 |
| JOIN | ❌ 불가 (일부 예외 있음) |
| 서브쿼리 | ❌ 불가 |
| UNION | ❌ 불가 |

**업데이트 가능한 단순 뷰 예시**

```sql
-- category_id=1인 전자기기만 노출하는 단순 뷰
CREATE OR REPLACE VIEW v_electronics AS
SELECT product_id, product_name, price, stock
FROM product
WHERE category_id = 1;

-- 뷰를 통해 재고 수량 업데이트 → 실제 product 테이블이 변경됨
UPDATE v_electronics
SET stock = 55
WHERE product_id = 1;

-- 확인
SELECT product_id, product_name, stock FROM product WHERE product_id = 1;
-- 결과: stock = 55 (원본 테이블이 변경됨)
```

**업데이트 불가능한 집계 뷰**

```sql
-- v_order_summary는 GROUP BY + 집계 함수 포함 → 업데이트 불가
UPDATE v_order_summary SET status = '배송완료' WHERE order_id = 7;
-- ERROR: The target table v_order_summary of the UPDATE is not updatable
```

## 7. 인덱스란?

**인덱스(Index)**는 데이터를 빠르게 찾기 위한 **색인(목차)**이다.  
책의 목차처럼 원하는 데이터가 어디에 있는지 가리켜 주어 전체를 처음부터 끝까지 읽지 않아도 된다.

### 인덱스 없이 검색 — 풀 테이블 스캔

```
고객 테이블 (100만 행)
┌────┬──────────┬─────────────────────┐
│ 1  │ 홍길동   │ hong@example.com    │
│ 2  │ 김영희   │ kim@example.com     │
│ 3  │ 이철수   │ lee@example.com     │
│ .. │ ...      │ ...                 │
│ 1M │ 마지막행  │ last@example.com    │
└────┴──────────┴─────────────────────┘

WHERE email = 'target@example.com'
→ 1행부터 마지막 행까지 모두 확인 (풀 테이블 스캔)
   데이터가 많을수록 느려짐
```

### 인덱스가 있을 때 — 인덱스 스캔

```
email 인덱스 (정렬된 B-Tree 구조)
hong@example.com  → 1번 행 가리킴
kim@example.com   → 2번 행 가리킴
lee@example.com   → 3번 행 가리킴
target@example.com → 해당 행 가리킴  ← 이진 탐색으로 빠르게 도달
```

인덱스를 사용하면 전체 데이터를 읽지 않고 원하는 행을 직접 찾아간다.

---

### 7.1 B-Tree 인덱스 구조

MariaDB의 기본 인덱스 구조는 **B-Tree(Balanced Tree)**다.  
데이터를 정렬된 트리 형태로 저장하여 검색·범위 조회 모두 빠르다.

```
              [35000]
             /       \
       [25000]        [55000]
       /     \        /     \
  [18000] [28000] [42000] [185000]
```

- 루트(root)에서 시작하여 크고 작음을 비교하며 내려가 원하는 값 탐색
- 데이터가 100만 건이어도 약 20번의 비교로 탐색 완료 (log₂(1,000,000) ≒ 20)

---

### 7.2 인덱스의 트레이드오프

인덱스는 **검색 속도를 높이지만 쓰기 속도와 저장 공간을 소모**한다.

| 항목 | 인덱스 없음 | 인덱스 있음 |
|---|:---:|:---:|
| SELECT 속도 | 느림 | 빠름 |
| INSERT 속도 | 빠름 | 느림 (인덱스 갱신 필요) |
| UPDATE 속도 | 빠름 | 느림 (인덱스 갱신 필요) |
| DELETE 속도 | 빠름 | 느림 (인덱스 갱신 필요) |
| 저장 공간 | 적음 | 추가 공간 필요 |

> **결론**: 자주 SELECT하고 드물게 변경하는 컬럼에 인덱스를 만들면 효과적이다.

## 8. 자동으로 생성되는 인덱스

테이블을 만들 때 **기본 키(PK)와 UNIQUE 제약**에는 자동으로 인덱스가 생성된다.

```sql
-- shopdb의 product 테이블에 이미 생성된 인덱스 확인
SHOW INDEX FROM product;
```

실행 결과:
```
+---------+------------+----------+--------------+-------------+
| Table   | Non_unique | Key_name | Seq_in_index | Column_name |
+---------+------------+----------+--------------+-------------+
| product |          0 | PRIMARY  |            1 | product_id  |
+---------+------------+----------+--------------+-------------+
```

- `Key_name = PRIMARY`: 기본 키 인덱스 (자동 생성)
- `Non_unique = 0`: 중복 불가 (PK이므로 당연)

## 9. 인덱스 생성 — CREATE INDEX

```sql
-- 기본 인덱스
CREATE INDEX 인덱스이름 ON 테이블이름(컬럼명);

-- 유일 인덱스 (중복 불가)
CREATE UNIQUE INDEX 인덱스이름 ON 테이블이름(컬럼명);

-- 복합 인덱스 (여러 컬럼)
CREATE INDEX 인덱스이름 ON 테이블이름(컬럼1, 컬럼2);
```

실행 결과:
```
+----------+------------+----------------------+--------------+-------------+
| Table    | Non_unique | Key_name             | Seq_in_index | Column_name |
+----------+------------+----------------------+--------------+-------------+
| customer |          0 | PRIMARY              |            1 | customer_id |
| customer |          0 | email                |            1 | email       |
| customer |          1 | idx_customer_email   |            1 | email       |
+----------+------------+----------------------+--------------+-------------+
```

> `email` 컬럼은 테이블 생성 시 `UNIQUE` 제약을 걸었으므로 이미 유일 인덱스가 있다. 중복으로 추가한 셈이 되므로 실제로는 하나만 유지한다. 여기서는 인덱스 생성 방법을 보여주기 위한 예제다.

---

### 9.2 복합 인덱스 — Composite Index

두 개 이상의 컬럼을 묶어서 하나의 인덱스로 만든다.  
**앞쪽 컬럼부터 순서대로 효과가 있다.**

```sql
-- orders 테이블: customer_id와 status를 함께 검색하는 쿼리가 많을 때
CREATE INDEX idx_orders_customer_status ON orders(customer_id, status);
```

이 인덱스가 효과 있는 WHERE 조건:
```sql
WHERE customer_id = 1                         -- ✅ 첫 번째 컬럼만 → 효과 있음
WHERE customer_id = 1 AND status = '배송완료' -- ✅ 두 컬럼 모두 → 효과 있음
WHERE status = '배송완료'                     -- ❌ 첫 번째 컬럼 생략 → 효과 없음
```

> **선두 컬럼 원칙**: 복합 인덱스는 WHERE 조건이 첫 번째 컬럼을 포함할 때만 인덱스를 사용할 수 있다.

---

### 9.3 인덱스 목록 조회

```sql
-- 특정 테이블의 인덱스 목록
SHOW INDEX FROM orders;

-- 테이블 정의와 함께 인덱스 확인
SHOW CREATE TABLE orders;
```

## 10. 실행 계획 분석 — EXPLAIN

**EXPLAIN**은 MariaDB가 쿼리를 어떻게 실행할지 계획을 보여준다.  
인덱스를 사용하는지, 풀 테이블 스캔인지 확인할 수 있다.

```sql
EXPLAIN SELECT 문장;
```

---

### 10.1 풀 테이블 스캔 확인

```sql
-- product 테이블에서 상품명으로 검색 (인덱스 없음)
EXPLAIN SELECT * FROM product WHERE product_name = '무선 마우스';
```

실행 결과:
```
+----+-------------+---------+------+---------------+------+---------+------+------+-------------+
| id | select_type | table   | type | possible_keys | key  | key_len | ref  | rows | Extra       |
+----+-------------+---------+------+---------------+------+---------+------+------+-------------+
|  1 | SIMPLE      | product | ALL  | NULL          | NULL | NULL    | NULL |   10 | Using where |
+----+-------------+---------+------+---------------+------+---------+------+------+-------------+
```

**주요 컬럼 해석**

| 컬럼 | 의미 |
|---|---|
| `type` | 접근 방식. **ALL = 풀 테이블 스캔** (데이터가 많으면 느림) |
| `possible_keys` | 사용 가능한 인덱스 목록 |
| `key` | **실제 사용된 인덱스** (NULL = 인덱스 미사용) |
| `rows` | 검색을 위해 읽은 예상 행 수 |
| `Extra` | 추가 정보 |

지금은 데이터가 10건밖에 없어 ALL이어도 빠르지만,  
100만 건이 되면 큰 차이가 난다.

---

### 10.2 인덱스 생성 후 EXPLAIN 비교

```sql
-- product_name 컬럼에 인덱스 생성
CREATE INDEX idx_product_name ON product(product_name);

-- 다시 EXPLAIN 실행
EXPLAIN SELECT * FROM product WHERE product_name = '무선 마우스';
```

실행 결과:
```
+----+-------------+---------+------+-------------------+-------------------+---------+-------+------+-------+
| id | select_type | table   | type | possible_keys     | key               | key_len | ref   | rows | Extra |
+----+-------------+---------+------+-------------------+-------------------+---------+-------+------+-------+
|  1 | SIMPLE      | product | ref  | idx_product_name  | idx_product_name  | 203     | const |    1 |       |
+----+-------------+---------+------+-------------------+-------------------+---------+-------+------+-------+
```

- `type = ref`: 인덱스를 사용한 검색 (ALL보다 훨씬 빠름)
- `key = idx_product_name`: 해당 인덱스 사용
- `rows = 1`: 1건만 읽어서 결과 반환

---

### 10.3 type 값의 의미 (좋은 순서)

| type 값 | 의미 | 속도 |
|---|---|:---:|
| `system` | 1행만 있는 테이블 | ⚡⚡⚡⚡⚡ |
| `const` | PK나 UNIQUE로 1행 검색 | ⚡⚡⚡⚡⚡ |
| `eq_ref` | JOIN 시 PK/UNIQUE 일치 검색 | ⚡⚡⚡⚡ |
| `ref` | 인덱스로 여러 행 검색 | ⚡⚡⚡ |
| `range` | 인덱스 범위 검색 (BETWEEN, >, <) | ⚡⚡ |
| `index` | 인덱스 전체 스캔 | ⚡ |
| `ALL` | 풀 테이블 스캔 (인덱스 미사용) | 🐢 |

> **최적화 목표**: type이 `ALL`인 쿼리를 찾아 인덱스를 추가하여 `ref` 이상으로 개선한다.

---

### 10.4 PK 검색과 EXPLAIN

기본 키로 검색하면 자동으로 `const`를 사용한다.

```sql
EXPLAIN SELECT * FROM customer WHERE customer_id = 1;
```

```
+----+-------------+----------+-------+---------------+---------+...+------+-------+
| id | select_type | table    | type  | possible_keys | key     |...| rows | Extra |
+----+-------------+----------+-------+---------------+---------+...+------+-------+
|  1 | SIMPLE      | customer | const | PRIMARY       | PRIMARY |...|    1 |       |
+----+-------------+----------+-------+---------------+---------+...+------+-------+
```

`const`: PK로 정확히 1개 행을 바로 찾음. 가장 빠른 접근 방식이다.

---

### 10.5 JOIN 쿼리의 EXPLAIN

```sql
EXPLAIN
SELECT o.order_id, c.name, o.status
FROM orders o
JOIN customer c ON o.customer_id = c.customer_id
WHERE c.name = '홍길동';
```

```
+----+-------------+-------+------+-------------------+---------+...+------+-------------+
| id | select_type | table | type | possible_keys     | key     |...| rows | Extra       |
+----+-------------+-------+------+-------------------+---------+...+------+-------------+
|  1 | SIMPLE      | c     | ALL  | PRIMARY           | NULL    |...|   10 | Using where |
|  1 | SIMPLE      | o     | ref  | idx_orders_cus..  | idx_..  |...|    2 |             |
+----+-------------+-------+------+-------------------+---------+...+------+-------------+
```

- `customer` 테이블은 `name` 컬럼에 인덱스가 없어 ALL 스캔
- `orders` 테이블은 `customer_id`에 인덱스가 있어 ref 스캔

`customer.name` 컬럼에 인덱스를 추가하면 두 테이블 모두 인덱스를 사용할 수 있다.

```sql
CREATE INDEX idx_customer_name ON customer(name);
```

## 11. 인덱스가 효과 없는 경우

아래의 경우에는 인덱스가 있어도 사용되지 않는다.

### 11.1 컬럼을 함수로 가공한 경우

```sql
-- ❌ 인덱스 사용 안 됨: 컬럼을 함수로 감싸면 인덱스 사용 불가
SELECT * FROM customer WHERE YEAR(created_at) = 2024;

-- ✅ 인덱스 사용 가능: 범위 조건으로 변경
SELECT * FROM customer
WHERE created_at BETWEEN '2024-01-01' AND '2024-12-31 23:59:59';
```

### 11.2 LIKE 앞쪽 와일드카드

```sql
-- ❌ 인덱스 사용 안 됨: 앞에 %가 있으면 전체 스캔 필요
SELECT * FROM customer WHERE email LIKE '%example%';

-- ✅ 인덱스 사용 가능: 앞은 고정, 뒤에만 %
SELECT * FROM customer WHERE email LIKE 'hong%';
```

### 11.3 데이터 형 불일치

```sql
-- customer_id는 INT, 문자열로 비교하면 묵시적 변환 → 인덱스 미사용
SELECT * FROM customer WHERE customer_id = '1';  -- ❌ (가능하나 비권장)
SELECT * FROM customer WHERE customer_id = 1;    -- ✅
```

### 11.4 OR 조건 (두 컬럼이 모두 인덱스 있을 때는 예외)

```sql
-- ❌ 보통 OR는 인덱스 하나만 사용
SELECT * FROM product WHERE product_name = '무선 마우스' OR price = 25000;

-- ✅ UNION으로 분리하면 각각 인덱스 사용
SELECT * FROM product WHERE product_name = '무선 마우스'
UNION
SELECT * FROM product WHERE price = 25000;
```

## 12. 인덱스 삭제 — DROP INDEX

```sql
DROP INDEX 인덱스이름 ON 테이블이름;
```

```sql
-- 앞에서 만든 인덱스 삭제
DROP INDEX idx_product_name ON product;
DROP INDEX idx_customer_name ON customer;
DROP INDEX idx_orders_customer_status ON orders;
```

> **주의**: PRIMARY KEY는 `DROP INDEX`가 아닌 `ALTER TABLE ... DROP PRIMARY KEY`로 삭제한다.  
> 단, PK를 먼저 삭제하면 외래 키 참조에 문제가 생길 수 있으니 주의한다.

## 13. 인덱스 설계 가이드

인덱스를 무조건 많이 만드는 것은 좋지 않다. 아래 기준으로 결정한다.

**인덱스를 만들어야 하는 경우**

- WHERE 조건에 자주 등장하는 컬럼
- JOIN의 ON 조건에 사용되는 외래 키 컬럼
- ORDER BY나 GROUP BY에 자주 사용되는 컬럼
- SELECT가 많고 INSERT/UPDATE/DELETE가 적은 테이블

**인덱스를 만들지 않는 것이 나은 경우**

- 행 수가 수백 건 이하인 작은 테이블
- INSERT/UPDATE/DELETE가 매우 빈번한 테이블 (갱신 오버헤드)
- 카디널리티(값의 종류)가 낮은 컬럼 (예: 성별 M/F, TRUE/FALSE)
- BLOB, TEXT처럼 길이가 매우 긴 컬럼

> **카디널리티(Cardinality)**: 컬럼에 있는 고유값의 수.  
> 카디널리티가 높을수록(예: 이메일, 주민번호) 인덱스 효과가 크고,  
> 낮을수록(예: 성별, 상태코드) 인덱스 효과가 작다.

   - `WHERE UPPER(email) = 'HONG@EXAMPLE.COM'`

> **정답**:
> ```sql

> ```

## 장 요약

### 뷰 (View) 정리

| 구문 | 설명 |
|---|---|
| `CREATE VIEW v이름 AS SELECT ...` | 뷰 생성 |
| `CREATE OR REPLACE VIEW v이름 AS SELECT ...` | 뷰 생성 또는 교체 |
| `SELECT * FROM v이름` | 뷰 조회 (일반 테이블과 동일) |
| `SHOW FULL TABLES WHERE Table_type = 'VIEW'` | 뷰 목록 확인 |
| `SHOW CREATE VIEW v이름` | 뷰 정의 확인 |
| `DROP VIEW IF EXISTS v이름` | 뷰 삭제 |

뷰를 통한 DML은 단일 테이블·집계 없는 단순 뷰에서만 가능하다.

### 인덱스 (Index) 정리

| 구문 | 설명 |
|---|---|
| `CREATE INDEX idx이름 ON 테이블(컬럼)` | 일반 인덱스 생성 |
| `CREATE UNIQUE INDEX idx이름 ON 테이블(컬럼)` | 유일 인덱스 생성 |
| `SHOW INDEX FROM 테이블` | 인덱스 목록 확인 |
| `EXPLAIN SELECT ...` | 실행 계획 확인 |
| `DROP INDEX idx이름 ON 테이블` | 인덱스 삭제 |

EXPLAIN의 `type = ALL`은 풀 테이블 스캔, `ref` 이상은 인덱스 사용을 의미한다.
