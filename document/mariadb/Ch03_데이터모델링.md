## 1. 요구사항 분석과 개념적 설계

### 1.1 왜 설계를 먼저 해야 하는가?

건물을 지을 때 설계도 없이 바로 공사를 시작하면 어떻게 될까?  
데이터베이스도 마찬가지다. 테이블을 먼저 만들고 나중에 수정하는 것은 건물을 다 짓고 벽을 허무는 것처럼 비효율적이다.

**설계 없이 구축한 데이터베이스의 문제점**

| 문제 | 결과 |
|---|---|
| 필요한 데이터를 저장할 공간이 없음 | 나중에 테이블 구조를 변경해야 하고, 기존 데이터가 영향을 받음 |
| 중복 데이터 발생 | 같은 정보가 여러 곳에 저장되어 수정 시 누락이 생김 |
| 테이블 간 관계 미정의 | 필요한 데이터를 조회할 수 없거나 복잡한 쿼리가 필요함 |

> **핵심 포인트**: 데이터베이스 설계는 집을 짓기 전에 그리는 설계도다. 시간이 걸리더라도 처음에 잘 설계하면 나중에 훨씬 적은 비용으로 유지·관리할 수 있다.

---

### 1.2 데이터베이스 설계 단계

데이터베이스 설계는 크게 세 단계로 진행된다.

```
요구사항 분석
     ↓
개념적 설계  →  ERD (개체 관계도) 작성
     ↓
논리적 설계  →  테이블 명세서 작성
     ↓
물리적 설계  →  실제 DBMS에 맞는 데이터 유형·제약조건 결정
     ↓
  구현 (SQL)
```

| 단계 | 산출물 | 설명 |
|---|---|---|
| **요구사항 분석** | 요구사항 명세서 | 무엇을 저장해야 하는지 파악 |
| **개념적 설계** | ERD | 개체·속성·관계를 그림으로 표현 |
| **논리적 설계** | 테이블 명세서 | ERD를 테이블 구조로 변환 |
| **물리적 설계** | CREATE TABLE SQL | DBMS에 맞게 데이터 유형·인덱스 결정 |

---

### 1.3 요구사항 분석

**요구사항 분석**이란 데이터베이스에 무엇을 저장하고, 어떻게 활용할지를 파악하는 과정이다.  
인터뷰, 설문, 업무 문서 분석 등의 방법으로 수행한다.

**분석 시 찾아야 할 세 가지**

| 찾을 것 | 설명 | 예시 |
|---|---|---|
| **개체 (Entity)** | 저장해야 할 대상(명사) | 고객, 상품, 주문 |
| **속성 (Attribute)** | 개체가 가진 특성 | 고객의 이름, 이메일, 연락처 |
| **관계 (Relationship)** | 개체 간의 연관성(동사) | 고객이 상품을 **주문한다** |

**예시: 온라인 쇼핑몰 요구사항**

> "고객은 회원 가입 시 이름, 이메일, 비밀번호, 연락처, 주소를 입력한다.  
> 고객은 여러 상품을 주문할 수 있으며, 하나의 주문에 여러 상품이 포함될 수 있다.  
> 상품은 카테고리로 분류되며, 상품명, 가격, 재고 수량, 설명 정보를 가진다.  
> 주문 시 주문일자, 배송지 주소, 결제 방법이 기록된다."

위 요구사항에서 개체·속성·관계를 추출하면:

**개체**
- 고객 (Customer)
- 상품 (Product)
- 카테고리 (Category)
- 주문 (Order)

**관계**
- 고객 **→ 주문한다 →** 상품
- 상품 **→ 속한다 →** 카테고리

## 2. 개체 관계도 ERD

### 2.1 ERD란?

**ERD(Entity-Relationship Diagram)**는 개체·속성·관계를 **그림으로 표현**한 데이터 모델이다.  
데이터베이스의 구조를 한눈에 파악할 수 있게 해주며, 개발자·기획자·고객이 함께 검토하는 공통 언어 역할을 한다.

---

### 2.2 ERD 표기법 — IE(까마귀 발) 표기법

이 강의에서는 실무에서 가장 널리 사용되는 **IE 표기법(Crow's Foot Notation)**을 사용한다.

**개체 (Entity)**

```
┌──────────────┐
│    고객       │   ← 개체명 (테이블이 됨)
├──────────────┤
│ *고객번호     │   ← * 는 기본 키(PK)
│  이름        │
│  이메일       │
│  연락처       │
│  주소        │
└──────────────┘
```

**관계 표현 — 카디널리티(Cardinality)**

두 개체 사이에 몇 개의 데이터가 대응되는지를 표현한다.

```
────────────    일(1)
────────────<   다(N, 여러 개)
────────────○   영(0, 없을 수도 있음)
────────────|   일(1, 반드시 하나)
```

| 관계 유형 | 표기 | 예시 |
|:---:|:---:|---|
| 1 : 1 | `\|────\|` | 직원 : 사원증 (한 직원은 하나의 사원증만 가짐) |
| 1 : N | `\|────<` | 고객 : 주문 (한 고객은 여러 주문을 할 수 있음) |
| M : N | `>────<` | 학생 : 강좌 (한 학생은 여러 강좌를 수강, 한 강좌에 여러 학생) |

---

### 2.3 카디널리티 이해하기

**1 : 1 관계**

한 개체의 한 행이 다른 개체의 정확히 한 행에 대응된다.

```
직원 |────────────| 사원증
     1            1
```
- 한 직원은 사원증을 하나만 가진다.
- 하나의 사원증은 한 명의 직원에게만 발급된다.

**1 : N 관계**

한 개체의 한 행이 다른 개체의 여러 행에 대응된다.  
관계형 데이터베이스에서 **가장 흔한 관계**다.

```
고객 |────────────< 주문
     1            N
```
- 한 고객은 여러 번 주문할 수 있다.
- 하나의 주문은 반드시 한 명의 고객에게만 속한다.

**M : N 관계**

한 개체의 여러 행이 다른 개체의 여러 행에 대응된다.  
데이터베이스에서는 M:N 관계를 **중간 테이블(연결 테이블)**로 분리하여 구현한다.

```
주문 >────────────< 상품
     M            N
```
- 하나의 주문에 여러 상품이 포함될 수 있다.
- 하나의 상품이 여러 주문에 포함될 수 있다.

```
→ 분리:  주문 |────< 주문상세 >────| 상품
```

---

### 2.4 쇼핑몰 ERD 예시

```
┌──────────────┐          ┌──────────────────┐          ┌──────────────┐
│   카테고리    │          │      상품         │          │    고객       │
├──────────────┤          ├──────────────────┤          ├──────────────┤
│ *카테고리번호  │          │ *상품번호          │          │ *고객번호     │
│  카테고리명   │          │  카테고리번호(FK)   │          │  이름        │
└──────────────┘          │  상품명            │          │  이메일       │
        |                 │  가격              │          │  연락처       │
        | 1               │  재고수량           │          │  주소        │
        |                 │  상품설명           │          └──────────────┘
        < N               └──────────────────┘                  | 1
        |                          | 1                          |
        |                          |                            < N
                                   < N                          |
                          ┌──────────────────┐                  |
                          │    주문상세        │        ┌──────────────────┐
                          ├──────────────────┤        │       주문        │
                          │ *주문상세번호      │        ├──────────────────┤
                          │  주문번호(FK)      │────────│ *주문번호          │
                          │  상품번호(FK)      │   N  1 │  고객번호(FK)      │
                          │  수량             │        │  주문일자          │
                          │  단가             │        │  배송지주소        │
                          └──────────────────┘        │  결제방법          │
                                                       └──────────────────┘
```

2. "한 부서에 여러 직원이 소속되고, 한 직원은 하나의 부서에만 소속된다"는 관계는 몇 대 몇 관계인가?

## 3. 정규화 — 왜 중복을 제거해야 하는가

### 3.1 이상 현상 (Anomaly)

정규화를 배우기 전에, 잘못 설계된 테이블에서 어떤 문제가 생기는지 먼저 살펴보자.

**잘못 설계된 주문 테이블 예시**

| 주문번호 | 고객이름 | 고객연락처    | 상품명    | 가격    | 수량 |
|:-------:|:------:|:-----------:|:--------:|:------:|:---:|
| 1001    | 홍길동  | 010-1111-1111 | 무선마우스  | 25,000 | 2   |
| 1001    | 홍길동  | 010-1111-1111 | USB허브   | 35,000 | 1   |
| 1002    | 김영희  | 010-2222-2222 | 무선마우스  | 25,000 | 1   |
| 1003    | 이철수  | 010-3333-3333 | 키보드     | 55,000 | 1   |

이 테이블에서는 세 가지 이상 현상이 발생한다.

**① 삽입 이상 (Insertion Anomaly)**

상품 정보를 먼저 등록하고 싶어도, 주문 정보가 없으면 삽입할 수 없다.  
(주문번호 컬럼이 비어 있으면 안 되기 때문)

**② 삭제 이상 (Deletion Anomaly)**

주문번호 1003을 삭제하면 이철수 고객의 정보도 함께 사라진다.  
단순히 주문 하나를 삭제했는데 고객 정보까지 잃어버리는 문제가 생긴다.

**③ 갱신 이상 (Update Anomaly)**

홍길동의 연락처가 바뀌면 해당 고객이 포함된 **모든 행**을 수정해야 한다.  
만약 1001번 주문의 두 행 중 하나만 수정하면 같은 고객의 연락처가 두 개가 된다.

> **결론**: 이런 이상 현상은 하나의 테이블에 서로 다른 주제의 데이터(고객 정보 + 주문 정보 + 상품 정보)가 뒤섞여 있기 때문에 발생한다. 정규화를 통해 각 테이블이 하나의 주제만 다루도록 분리한다.

---

### 3.2 정규화 (Normalization)

**정규화**란 데이터 중복과 이상 현상을 줄이기 위해 테이블을 체계적으로 분리하는 과정이다.  
단계별로 규칙(정규형)이 있으며, 높은 단계일수록 더 엄격한 규칙이 적용된다.

이 강의에서는 실무에서 가장 중요한 **1NF, 2NF, 3NF**를 학습한다.

---

### 3.3 제1정규형 (1NF)

**규칙**: 모든 열의 값은 원자값(더 이상 분리할 수 없는 단일 값)이어야 한다.

**위반 예시**

| 주문번호 | 고객명 | 구매 상품 |
|:-------:|:-----:|:--------:|
| 1001    | 홍길동 | 무선마우스, USB허브 |
| 1002    | 김영희 | 무선마우스 |

`구매 상품` 열에 여러 값이 들어가 있으므로 1NF를 위반한다.

**1NF 적용 후**

| 주문번호 | 고객명 | 구매 상품 |
|:-------:|:-----:|:--------:|
| 1001    | 홍길동 | 무선마우스 |
| 1001    | 홍길동 | USB허브  |
| 1002    | 김영희 | 무선마우스 |

각 열의 값이 원자값이 되었다.

---

### 3.4 제2정규형 (2NF)

**규칙**: 1NF를 만족하고, 기본 키가 복합 키일 때 모든 일반 속성이 기본 키 **전체**에 종속되어야 한다.  
(기본 키의 일부에만 종속되는 **부분 종속**을 제거한다.)

**위반 예시** (기본 키: 주문번호 + 상품번호)

| **주문번호** | **상품번호** | 수량 | 고객명 | 상품명   | 가격    |
|:-----------:|:-----------:|:---:|:-----:|:-------:|:------:|
| 1001        | P001        | 2   | 홍길동  | 무선마우스 | 25,000 |
| 1001        | P002        | 1   | 홍길동  | USB허브  | 35,000 |
| 1002        | P001        | 1   | 김영희  | 무선마우스 | 25,000 |

- `수량`은 주문번호 **+** 상품번호 모두에 종속 → 정상
- `고객명`은 주문번호에만 종속 → **부분 종속** (위반)
- `상품명`, `가격`은 상품번호에만 종속 → **부분 종속** (위반)

**2NF 적용 후** — 부분 종속을 별도 테이블로 분리

**주문 테이블**

| **주문번호** | 고객명 |
|:-----------:|:-----:|
| 1001        | 홍길동  |
| 1002        | 김영희  |

**상품 테이블**

| **상품번호** | 상품명   | 가격    |
|:-----------:|:-------:|:------:|
| P001        | 무선마우스 | 25,000 |
| P002        | USB허브  | 35,000 |

**주문상세 테이블**

| **주문번호** | **상품번호** | 수량 |
|:-----------:|:-----------:|:---:|
| 1001        | P001        | 2   |
| 1001        | P002        | 1   |
| 1002        | P001        | 1   |

---

### 3.5 제3정규형 (3NF)

**규칙**: 2NF를 만족하고, 기본 키가 아닌 일반 속성이 다른 일반 속성에 종속되는 **이행 종속**을 제거한다.

**위반 예시** (기본 키: 직원번호)

| **직원번호** | 직원명 | 부서코드 | 부서명 |
|:-----------:|:-----:|:-------:|:-----:|
| E001        | 홍길동  | D01     | 개발팀  |
| E002        | 김영희  | D01     | 개발팀  |
| E003        | 이철수  | D02     | 영업팀  |

- `부서명`은 `부서코드`에 종속되고, `부서코드`는 `직원번호`에 종속된다.
- 즉, `부서명`은 기본 키인 `직원번호`가 아닌 `부서코드`에 이행 종속 → 위반

부서 코드 D01의 부서명이 바뀌면 해당 부서 모든 직원의 행을 수정해야 한다.

**3NF 적용 후** — 이행 종속을 별도 테이블로 분리

**직원 테이블**

| **직원번호** | 직원명 | 부서코드(FK) |
|:-----------:|:-----:|:-----------:|
| E001        | 홍길동  | D01         |
| E002        | 김영희  | D01         |
| E003        | 이철수  | D02         |

**부서 테이블**

| **부서코드** | 부서명 |
|:-----------:|:-----:|
| D01         | 개발팀  |
| D02         | 영업팀  |

---

### 3.6 정규화 요약

```
원본 테이블
    ↓
[1NF] 열의 값을 원자값으로 분리
    ↓
[2NF] 부분 종속 제거 (복합 PK의 일부에만 종속되는 컬럼 분리)
    ↓
[3NF] 이행 종속 제거 (일반 컬럼이 다른 일반 컬럼에 종속되는 경우 분리)
```

> **실무 팁**: 3NF까지 정규화하면 대부분의 이상 현상이 해결된다. 그러나 지나친 정규화는 JOIN이 많아져 조회 성능이 떨어질 수 있으므로, 실무에서는 성능을 고려하여 의도적으로 일부 비정규화(denormalization)를 적용하기도 한다.

아래 테이블을 보고 물음에 답하시오.

| **학번** | **과목코드** | 학생명 | 과목명   | 학점 | 담당교수 |
|:-------:|:-----------:|:-----:|:-------:|:---:|:------:|

| S001    | C002        | 홍길동  | 파이썬    | B+  | 이교수   |
| S002    | C001        | 김영희  | 데이터베이스 | B  | 김교수   |

2. 어떤 속성이 부분 종속되어 있는가? (2NF 위반)
3. 이행 종속이 존재한다면 어떤 속성인가? (3NF 위반)
4. 3NF까지 정규화하여 테이블을 분리하시오.

>    - **학생** (학번 PK, 학생명)  
>    - **과목** (과목코드 PK, 과목명, 담당교수)  
>    - **수강** (학번 FK, 과목코드 FK, 학점)

## 4. 논리적 설계 → 물리적 설계

### 4.1 논리적 설계

**논리적 설계**는 ERD를 실제 테이블 구조로 변환하는 단계다.  
각 개체는 테이블이 되고, 속성은 열(컬럼)이 된다.

**ERD → 테이블 변환 규칙**

| ERD 요소 | 테이블 요소 |
|---|---|
| 개체 (Entity) | 테이블 (Table) |
| 속성 (Attribute) | 컬럼 (Column) |
| 기본 키 속성 | PRIMARY KEY |
| 관계 (1:N) | 자식 테이블에 외래 키(FK) 추가 |
| M:N 관계 | 중간 테이블 생성, 각 테이블의 PK를 FK로 포함 |

**M:N 관계 처리 예시**

```
[ERD]
주문 >────────< 상품

[변환 후]
주문 |────< 주문상세 >────| 상품
```

주문상세 테이블에 주문번호(FK), 상품번호(FK)를 함께 포함시켜 M:N을 두 개의 1:N으로 분리한다.

---

### 4.2 물리적 설계

**물리적 설계**는 논리적 설계에 실제 DBMS(MariaDB)에서 사용하는 **데이터 유형과 제약조건**을 결정하는 단계다.

> 데이터 유형의 상세 내용은 Chapter 4(DDL)에서 학습한다. 여기서는 대표적인 유형만 확인한다.

**자주 사용하는 데이터 유형**

| 유형 | 설명 | 예시 |
|---|---|---|
| `INT` | 정수 | 수량, 나이, 번호 |
| `DECIMAL(p, s)` | 소수점 포함 숫자 | 가격 (DECIMAL(10,2)) |
| `VARCHAR(n)` | 가변 길이 문자열 | 이름, 이메일, 주소 |
| `CHAR(n)` | 고정 길이 문자열 | 우편번호, 성별 코드 |
| `DATE` | 날짜 (YYYY-MM-DD) | 생년월일, 주문일 |
| `DATETIME` | 날짜 + 시간 | 로그인 시간, 등록일시 |
| `TEXT` | 긴 문자열 | 상품 설명, 게시글 내용 |

## 5. 실습 DB 설계

이 강의 전체에서 사용할 **온라인 쇼핑몰 데이터베이스**를 설계한다.  
앞서 학습한 요구사항 분석 → ERD → 논리적/물리적 설계 과정을 직접 적용한다.

---

### 5.1 요구사항 정의

> 온라인 쇼핑몰 시스템을 위한 데이터베이스를 설계한다.
>
> - 고객은 이름, 이메일(로그인 ID), 비밀번호, 연락처, 주소, 가입일을 가진다.
> - 상품은 카테고리로 분류되며, 상품명, 가격, 재고수량, 상품설명, 등록일을 가진다.
> - 카테고리는 카테고리명을 가진다.
> - 고객은 여러 번 주문할 수 있으며, 주문 시 주문일자, 배송지 주소, 결제방법, 주문상태가 기록된다.
> - 하나의 주문에는 여러 상품이 포함될 수 있으며, 각 상품의 주문 수량과 주문 당시의 단가가 기록된다.

---

### 5.2 개체 및 관계 도출

**개체 목록**

| 개체 (한글) | 테이블명 (영문) | 설명 |
|:----------:|:-------------:|---|
| 고객 | customer | 쇼핑몰 회원 정보 |
| 카테고리 | category | 상품 분류 |
| 상품 | product | 판매 상품 정보 |
| 주문 | orders | 고객의 주문 정보 |
| 주문상세 | order_detail | 주문에 포함된 상품별 수량·단가 |

**관계 목록**

| 관계 | 유형 | 설명 |
|---|:---:|---|
| 고객 : 주문 | 1 : N | 한 고객은 여러 번 주문할 수 있다 |
| 카테고리 : 상품 | 1 : N | 한 카테고리에 여러 상품이 속한다 |
| 주문 : 주문상세 | 1 : N | 한 주문에 여러 주문상세가 있다 |
| 상품 : 주문상세 | 1 : N | 한 상품은 여러 주문상세에 포함될 수 있다 |

---

### 5.3 테이블 명세서 (물리적 설계)

**① customer (고객)**

| 컬럼명 | 데이터 유형 | 제약 조건 | 설명 |
|---|---|---|---|
| customer_id | INT | PRIMARY KEY, AUTO_INCREMENT | 고객번호 |
| name | VARCHAR(50) | NOT NULL | 이름 |
| email | VARCHAR(100) | NOT NULL, UNIQUE | 이메일 (로그인 ID) |
| password | VARCHAR(255) | NOT NULL | 비밀번호 (암호화 저장) |
| phone | CHAR(13) | | 연락처 (010-0000-0000) |
| address | VARCHAR(200) | | 주소 |
| created_at | DATETIME | DEFAULT NOW() | 가입일시 |

**② category (카테고리)**

| 컬럼명 | 데이터 유형 | 제약 조건 | 설명 |
|---|---|---|---|
| category_id | INT | PRIMARY KEY, AUTO_INCREMENT | 카테고리번호 |
| category_name | VARCHAR(50) | NOT NULL, UNIQUE | 카테고리명 |

**③ product (상품)**

| 컬럼명 | 데이터 유형 | 제약 조건 | 설명 |
|---|---|---|---|
| product_id | INT | PRIMARY KEY, AUTO_INCREMENT | 상품번호 |
| category_id | INT | FOREIGN KEY → category | 카테고리번호 |
| product_name | VARCHAR(100) | NOT NULL | 상품명 |
| price | DECIMAL(10, 0) | NOT NULL | 판매가격 |
| stock | INT | NOT NULL, DEFAULT 0 | 재고수량 |
| description | TEXT | | 상품설명 |
| created_at | DATETIME | DEFAULT NOW() | 등록일시 |

**④ orders (주문)**

| 컬럼명 | 데이터 유형 | 제약 조건 | 설명 |
|---|---|---|---|
| order_id | INT | PRIMARY KEY, AUTO_INCREMENT | 주문번호 |
| customer_id | INT | FOREIGN KEY → customer | 고객번호 |
| order_date | DATETIME | DEFAULT NOW() | 주문일시 |
| shipping_address | VARCHAR(200) | NOT NULL | 배송지 주소 |
| payment_method | VARCHAR(20) | NOT NULL | 결제방법 (카드/현금/포인트) |
| status | VARCHAR(20) | DEFAULT '주문완료' | 주문상태 |

**⑤ order_detail (주문상세)**

| 컬럼명 | 데이터 유형 | 제약 조건 | 설명 |
|---|---|---|---|
| detail_id | INT | PRIMARY KEY, AUTO_INCREMENT | 주문상세번호 |
| order_id | INT | FOREIGN KEY → orders | 주문번호 |
| product_id | INT | FOREIGN KEY → product | 상품번호 |
| quantity | INT | NOT NULL | 수량 |
| unit_price | DECIMAL(10, 0) | NOT NULL | 주문 당시 단가 |

> **unit_price를 별도로 저장하는 이유**: 상품의 가격은 나중에 변경될 수 있다. 주문 당시의 가격을 별도로 기록해 두지 않으면, 나중에 가격이 변경되었을 때 과거 주문의 결제 금액을 계산할 수 없게 된다.

### 5.4 테이블 관계도

```
category (카테고리)
    | 1
    | category_id
    < N
product (상품) ──────────────────────────────────┐
    | 1                                          | 1
    | product_id                                 |
    < N                                          < N
order_detail (주문상세)                           |
    > N                                          |
    | order_id                                   |
    | 1                                          |
orders (주문) ────── customer_id(FK) ──── customer (고객)
                                          1
```

### ✅ 확인 문제 5

1. `order_detail` 테이블에 `unit_price` 컬럼을 별도로 두는 이유는 무엇인가?
2. `orders` 테이블과 `customer` 테이블의 관계를 설명하고, 어떤 컬럼이 외래 키 역할을 하는가?
3. `product` 테이블에서 `stock` 컬럼의 기본값을 0으로 설정한 이유는 무엇인가?

> **정답**:  
> 1. 상품 가격은 이후에 변경될 수 있으므로, 주문 당시의 가격을 고정하여 보관하기 위함이다. `product.price`만 참조하면 가격 변경 시 과거 주문 금액 계산이 불가능하다.  
> 2. 1:N 관계이며 (한 고객이 여러 주문을 할 수 있음), `orders.customer_id`가 `customer.customer_id`를 참조하는 외래 키다.  
> 3. 새 상품을 등록할 때 재고 수량 입력을 빠뜨렸을 경우에도 NULL이 아닌 0으로 저장되어, 이후 재고 관련 계산에서 오류가 발생하지 않도록 하기 위함이다.

## 장 요약

| 개념 | 핵심 내용 |
|---|---|
| **설계 단계** | 요구사항 분석 → 개념적(ERD) → 논리적(명세서) → 물리적(SQL) 설계 |
| **개체 (Entity)** | 저장해야 할 대상, 테이블이 됨 |
| **속성 (Attribute)** | 개체의 특성, 컬럼이 됨 |

| **이상 현상** | 삽입·삭제·갱신 이상 — 잘못된 설계에서 발생 |
| **1NF** | 열의 값은 원자값(단일 값)이어야 함 |
| **2NF** | 부분 종속 제거 (복합 PK일 때) |
| **3NF** | 이행 종속 제거 (일반 컬럼 간 종속 제거) |
| **실습 DB** | 온라인 쇼핑몰 (customer, category, product, orders, order_detail) |
